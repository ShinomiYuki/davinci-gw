# 第05轮开发日志：纯本地 STDIO MCP 产品化

## 目标与范围

本轮以第04轮稳定的 `GatewayFacade`、公共 DTO、`ProgressObserver` 和 `CancellationToken` 为唯一业务边界，交付可由 Codex 等本地客户端启动的 Windows x64 STDIO MCP。没有开发 GUI、HTTP/SSE/WebSocket 服务、端口监听、OAuth、云端调用、遥测或自动更新；没有修改真实 Codex 配置，也不发布远程 Release。

版本从 `0.1.0` 提升为 `0.2.0`，原因是首次增加对外可安装、具有稳定工具协议的 MCP 产品面，同时保持原 CLI 行为和核心运行依赖不变。MCP SDK 作为 `mcp` 可选依赖，开发/打包环境使用官方 Python SDK `mcp>=2.1,<3`。

## 官方 Codex 与 MCP 契约

实现前依据 Codex 官方 MCP 文档确认：本地服务可以由 `command` 启动为 STDIO；用户配置位于 `~/.codex/config.toml`；服务 instructions 的前 512 字符需要自包含；配置支持启动/工具超时、启用状态、工具白名单与审批模式。安装模板采用 `default_tools_approval_mode = "writes"`，并对 `generate_gateway_arxml` 显式设置 `approval_mode = "prompt"`。

SDK 使用 2.x 维护分支的 `MCPServer`、`ToolAnnotations`、结构化输出和 lifespan。运行入口硬编码 `transport="stdio"`，没有从命令行或环境开放其他 transport。

## 四个稳定工具

| 工具 | 语义 | annotations |
| --- | --- | --- |
| `get_gateway_capabilities` | 版本、功能、工作流和安全策略 | read-only, non-destructive, idempotent, closed-world |
| `validate_gateway_inputs` | 只读联合校验 | read-only, non-destructive, idempotent, closed-world |
| `preview_gateway_update` | 完整规划并建立一次性会话 | read-only, non-destructive, non-idempotent, closed-world |
| `generate_gateway_arxml` | 提交已确认会话到新文件 | write, destructive, non-idempotent, closed-world |

服务进程仅构造一个 `GatewayFacade`。预览结果中的公共 `preparation_id` 与基准规范路径形成轻量安全索引；真实 ARXML 工作树仍只由核心 `PreparedSessionStore` 持有，MCP 不解析 XML、不复制事务、不读取私有 Session 记录。生成工具不接受配置表或基准路径，因此不能绕过预览重新计算。

## 协议输出

四个工具统一返回 schema `1.0` 的 JSON 对象：工具名、操作 ID、公共状态、成功标志、摘要、问题总数、截断标志、错误优先的问题列表和该工具的结构化负载。问题最多 200 条，字符串、集合深度/条数和整体响应均受限，最终 JSON 上限为 512000 字节。响应不包含 XML/Base64、lxml 节点、内部事务、异常对象或 traceback。

stdout 仅由官方 SDK 写 MCP JSON-RPC。应用日志优先写 `%LOCALAPPDATA%\DaVinciGW\logs\mcp.log`，1 MB 滚动、3 个备份；目录不可用时仅回退 stderr。日志观察者只记录 operation/stage/percent/cancellable，不记录文件内容、完整请求或路径参数。

## 路径和覆盖策略

边界只接受带盘符的 Windows 本地绝对路径。相对路径、URL、UNC/扩展 UNC、设备/命名管道、网络共享、备用数据流、控制字符、非法尾缀和保留设备名在进入 Facade 前拒绝。输入必须是后缀正确的现有普通文件。

输出父目录必须已经存在，目标必须是尚不存在的 `.arxml`。规范路径、大小写折叠、`realpath` 和可用时的 `samefile` 共同保护基准；符号链接或目录联接解析后的别名也不能覆盖基准。MCP 永远以 `overwrite=False` 调用 `commit_prepared`，且不自动创建输出目录。

## 并发、取消与退出

所有重操作通过每进程单个 `ThreadPoolExecutor(max_workers=1)` 和异步信号量串行化。每次调用创建独立 `CancellationToken`；JSON-RPC 任务取消会先设置令牌，再等待同步 Facade 在安全检查点收尾，然后传播协议取消。lifespan 在 stdin EOF/正常关闭时取消全部活动令牌、释放未提交会话，并等待工作线程退出，避免后台线程或临时输出泄漏。

核心的两次输入指纹复核、原子临时文件验证和发布前取消边界继续决定最终提交语义；MCP 不用文本推断成功或失败。

## EXE、发布与安装

PyInstaller spec 生成 `console=True` 的 Windows x64 单文件 EXE，保留 stdin/stdout/stderr。版本资源固定为 0.2.0。项目根目录采用标准 MIT License，构建脚本将其作为 `LICENSE.txt` 放入发布包。ZIP 还包含 EXE、安装/卸载脚本、配置示例、文档、版本和 EXE SHA-256，并在 ZIP 旁生成归档 SHA-256。二进制与归档位于 `release/` 且被 Git 忽略。

安装器只操作显式用户级目录，复制前核对 SHA-256；不同旧 EXE 和 Codex 配置在修改前备份。配置以带 begin/end 标记的托管块更新；遇到非托管同名服务立即停止。相同包重复安装不会重复配置。卸载器只移除托管块、EXE 与清单，不递归删除用户目录或备份。

## 验证记录

最终实际证据如下：

- pytest 以互补分组完成完整回归：non-slow `165 passed, 5 deselected`；slow `5 passed, 165 deselected`，合计 170 项、无重复失败。slow 分组包含原真实 Excel/大型 ARXML、真实 STDIO 取消和最终 EXE 测试。
- 官方 MCP 客户端驱动 Python 模块子进程完成 initialize、tools/list、preview、generate；四个工具、instructions、annotations、input/output schema 与 structuredContent 均通过。
- 最终单文件 EXE 在移除 Python/PYTHONPATH、PATH 仅保留 System32、工作目录不含源码且代理指向无效地址时，完成 validate、preview、generate。EXE 进程未发现 TCP 连接，stdin EOF 后退出码为 0。
- socket API 被测试替换为立即失败时，四工具完整流程仍成功；源代码静态检查未发现网络 API、CLI、lxml 或内部事务依赖。
- 真实 STDIO 请求取消后，同一服务进程仍可响应；单线程执行器并发上限、令牌桥接、无临时输出和 EOF 退出均有回归。
- 安装/重复安装/卸载、篡改包拒绝、非托管同名配置拒绝、篡改已安装 EXE 拒绝均在 pytest 临时目录通过；既有 Codex 配置得到保留并在修改前备份。
- 使用仓库 `build/final-package-validation` 作为临时 `CODEX_HOME`，Codex CLI `0.150.0-alpha.8` 成功识别 enabled 的 stdio 服务、30 秒启动超时、3600 秒工具超时和 `writes` 默认审批；临时 TOML 明确包含生成工具 `approval_mode = "prompt"`。没有修改真实用户配置。
- 最终 EXE 大小 232481064 字节，SHA-256 为 `d3b8f6cfd1c369f1addbfca2a8d5d5d81687c578f3a1c26d787d8d41d43817af`；ZIP 大小 230990065 字节，SHA-256 为 `7bdab85e80b05914c35fe13688d35781d8a4afe2743d2a75bc276f68ade0f5ee`。ZIP 的 8 个必需文件、内层 EXE 校验和和 MIT License 均已核对，并用包内脚本完成隔离安装、Codex 发现和卸载。
- 当前主机没有提供真正无 Python 的裸 Windows 或 Windows Sandbox，因此准确结论是“清空 Python/PATH/PYTHONPATH 的独立 EXE 子进程验证”，不宣称物理隔离或真正 air-gapped 环境。

如当前主机无法提供真正无 Python 的裸 Windows 或 Windows Sandbox，日志只会表述为“清空 Python/PATH/PYTHONPATH 的独立 EXE 子进程验证”，不会把它夸大为物理隔离或真正 air-gapped 测试。
