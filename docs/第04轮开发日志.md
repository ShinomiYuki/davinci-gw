# 第04轮开发日志：公共应用接口与可扩展架构

## 本轮目标

在不开发 GUI、本地 MCP 服务或安装进程的前提下，为两类未来适配器建立唯一公共核心入口。公共边界必须稳定序列化、不可变且不泄漏 lxml、`ArxmlDocument`、`MutationPlan`、异常对象或 traceback；现有 CLI 行为保持兼容。

修改前位于 `main`，HEAD 为第03轮提交 `e7ed363d09d797fc5c7a14cf154869ca3bea1445`，工作区干净；仓库没有额外 `AGENTS.md`。运行依赖仍只有 openpyxl 与 lxml，开发依赖为 pytest，本轮没有增加或升级依赖。

基线总数为 113；真实 ARXML 为约 81 MB。修改前已具备直接报文/信号 ADD 与 DELETE、DELETE→ADD 内存事务、输出复核、基线保护和原子写出。

## 最终架构

依赖方向为：

```text
未来 GUI / 本地 MCP
        ↓
contracts + GatewayFacade + ProgressObserver/CancellationToken
        ↓
Feature / Prepared Session / 公共映射
        ↓
现有 application / routing / domain / arxml / modules
```

contracts 不导入 application、routing、ARXML 或 lxml。Feature 注册机制只负责能力和统计投影，不重写稳定规划器；MutationHandler 只替换适合扩展的应用分派。内部会话记录持有一次 `PreparedTransaction`，公共会话 DTO 只持有 UUID、时间、状态和预览。

## 公共契约与 Facade

`davinci_gw.contracts` 定义 schema 版本 `1.0` 以及请求、输入文件与指纹、问题、状态、动态指标、Feature 汇总、进度、产物、预览、Prepared Session、生成结果和能力 DTO。全部 DTO 使用冻结 dataclass 和字符串枚举；路径转换为字符串，Decimal 等输入值转换为 JSON 安全值。`to_dict()` 只产生字典、列表和 JSON 标量，未知或内部对象统一变为 `<unsupported>`，异常对象不会越过公共边界。

`GatewayFacade` 提供：

- `capabilities()` / `get_capabilities()`：返回动态 Feature 与可用操作。
- `validate()`：联合校验配置表与基准 ARXML。
- `prepare()` / `preview()`：一次完成解析、规划和内存应用，并建立会话。
- `commit_prepared()`：复用会话中的工作树，校验后原子发布。
- `generate()`：以 prepare→commit 组合完成一次性生成。
- `discard_prepared()` / `cleanup_expired()`：主动释放和过期清理。

公共状态稳定区分成功、校验失败、取消、会话不存在/过期/无效/已消费、输入变化和内部失败。预期内部错误映射为结构化问题；未预期异常只返回受控中文消息，不包含异常链。

## 动态 Feature

`RoutingFeature` 协议描述稳定标识、显示名、能力和 `summarize()`。`FeatureRegistry` 为实例级注册表，保持注册顺序并显式拒绝重复标识。默认 `DirectMessageFeature` 与 `SignalRoutingFeature` 将现有工作簿和计划统计投影为 `MetricDto` 集合，公共 DTO 和 Facade 不再包含固定的 `direct_message_count`、`signal_route_count` 字段。

测试注册了一个虚拟诊断 Feature；未修改 Facade 或 DTO 即同时出现在 capabilities 和预览统计中，证明扩展入口成立。

## MutationHandler 注册表

原 `AddCoordinator.apply()` 的 `if/elif` 模块分派改为 `MutationHandlerRegistry`。每个处理器声明稳定 ID、负责的 `MutationKind`、顺序和应用函数。注册表统一完成：

- 重复 handler ID 和重复 kind 检测；
- 未知 kind 显式报错；
- 先按处理器顺序、再按对象路径确定排序；
- 无核心条件分支的处理器调用。

默认处理器完整保留原顺序：EcuC 10，CanIf Rx/Tx 20/30，PduR Path/Src/Dest 40/50/60，Com Mapping/Source/Destination/Timeout 70/80/90/100。

## 进度与协作取消

`ProgressReporter` 输出操作 UUID、单调 sequence、稳定 stage、当前值、总值、百分比和是否可取消。成功以 `complete` 结束，失败以 `error` 结束，取消以 `cancelled` 结束。观察者调用由 `try/except` 隔离，前端回调故障不会改变事务结果。

`CancellationToken` 使用线程事件，只在工作簿读取前后、基准解析后、规划前后、指纹复核、临时写出前和原子替换前等安全边界响应。预览取消只丢弃内存树；原子替换前取消由 `OutputCommitAbortedError` 穿过 ARXML 写出层，`finally` 删除同目录临时文件。`os.replace` 成功后不再检查取消，避免把已提交文件误报为取消。

## Prepared Session

会话存储在单个进程内，默认 TTL 为 900 秒、容量为 8。每条记录包含不透明 UUID、UTC 创建/到期时间、单调时钟到期点、状态、请求、配置表与基准指纹、内部 `PreparedTransaction` 和公共预览。TTL 只依赖单调时钟，避免系统时钟回拨影响。

预览建立会话前，会比较规划前后的输入指纹；提交开始和原子替换前再次比较。指纹包含解析后的绝对路径、文件大小、纳秒修改时间与 SHA-256。任一变化返回 `INPUT_CHANGED`，不发布目标。

状态转换在锁内完成：`READY → COMMITTING → CONSUMED`。并发提交只有一个调用能取得 `COMMITTING`；其余返回会话无效或已消费。提交失败/取消后状态变为 `INVALID`，成功或失效时立即释放内部工作树。过期会话保留轻量墓碑以区分 `EXPIRED`，容量不足时按最早创建记录淘汰；显式释放进入 `INVALID`。公共 DTO 只保存会话标识和预览，不保存工作树。

## CLI 兼容选择

CLI 继续调用既有 `validate_inputs()`、`preview_inputs()` 与 `generate_inputs()`。这是有意的兼容边界：本轮不扩大为 CLI 输出重构，确保原退出码、文本和调试异常链保持已有测试覆盖。未来 GUI 与 MCP 只依赖 `GatewayFacade`；两者不会反向依赖 CLI。

## 相对指导方案的调整

- contracts 规模仍较小，因此集中在 `contracts/models.py`，避免为每类仅数十行的 DTO 建立过多文件；对外仍由 `contracts/__init__.py` 提供稳定导出。
- Feature 的 `FeatureContext` 是内部适配上下文，可以读取现有不可变 `WorkbookData` 与 `MutationPlan`；只有 `FeatureSummaryDto` 能越过 Facade。这样避免为可扩展性重写已稳定的规划器。
- Prepared Session Store 采用具体实例注入而非新增抽象基类。它已经可在测试和不同适配器中替换，暂不引入只有一个实现的接口层。
- 过期、消费和失效会话保留轻量墓碑，使调用者得到不同状态；内部工作树立即释放，容量策略仍能淘汰墓碑。
- CLI 没有切换到 Facade，原因是一步生成的 Prepared Session 语义和现有 CLI 文本生命周期不同；保持旧链路能控制本轮风险。

## 代码审查发现—修复—验证

1. **变更类型细分顺序可能被合并**：首版按四个模块给处理器排序，会让同模块不同 kind 改按路径排序。修复为每个 kind 单独注册，恢复原 10～100 精确顺序。
2. **扩展元数据可能携带内部对象**：仅依赖类型标注不能阻止运行时传入 `MutationPlan`。修复 DTO 序列化和元数据归一化，非公共 dataclass 与未知对象统一为 `<unsupported>`，并增加内部对象不可序列化测试。
3. **系统异常已从 cause 移除但可能残留在 message**：修复系统失败代码的公共映射，改为受控中文消息，不回显原异常。
4. **提交失败缺少终态进度事件**：修复会话错误、输入变化、取消、输出拒绝和未预期错误分支，统一发送 `error` 或 `cancelled`。
5. **原子替换后读取产物指纹失败可能误报整个提交失败**：修复为替换成功即固定返回成功；产物元数据读取异常时提供不含哈希的降级 Artifact，不改变已提交事实。
6. **默认 MutationHandler 顺序兼容性**：定向执行原应用、ARXML、直接报文、信号和新增注册表测试，确认原模块调用链未改变。
7. **相对输入路径可能随工作目录漂移**：首版会话保存调用方原始请求，若预览后进程切换工作目录，提交可能解析到另一文件。修复为会话创建时冻结配置表与基准的规范绝对路径，并增加切换目录后仍能提交的回归。
8. **一步生成出现两个操作 ID 和过早完成事件**：首版直接把同一观察者传入 prepare 与 commit，前端会看到两套 sequence，且 prepare 完成可能被误解为生成完成。修复为组合进度适配器，把两个内部阶段折叠到一个操作 ID、单调序号和唯一终态事件。
9. **输出写入失败状态过于笼统**：修复为输出契约/复核拒绝返回 `VALIDATION_FAILED`，带底层 I/O 原因的写入失败返回 `INTERNAL_FAILURE`；两类都只公开受控消息并清理临时文件。

## 性能与内存观察

Prepared Session 不复制 81 MB ARXML 树，预览后提交只复用同一棵已应用工作树；成功、失败、取消、过期或主动释放均清空该引用。默认最多 8 个会话，调用方若预计并行处理多个大工程应按可用内存降低容量。

为防止使用陈旧预览，SHA-256 会在预览前后、提交开始和发布前读取输入。这增加顺序文件 I/O，但不增加等量内存；ARXML 摘要以 1 MiB 块流式计算。最终两条真实慢速测试合计 54.31 s，修改前为 55.64 s；在本机样本和测试范围内没有观察到明显回退。

## 下一阶段复用方式

GUI 应在自己的工作线程中同步调用 Facade，用观察者把 `ProgressEventDto` 转为界面事件，并保存 `session_id` 供用户确认；MCP 工具应把 DTO 的 `to_dict()` 直接作为结构化结果。两者都应在输入变化、过期或失效时重新调用 `preview()`，不缓存内部对象，也不依赖 CLI 文本。GUI/MCP 的协议、鉴权、进程模型和部署不属于本轮。

## 已知限制

- Prepared Session 仅为当前 Python 进程内状态，不支持跨进程、持久化或分布式锁。
- 指纹在原子替换前立即复核，但普通文件系统无法提供跨两个输入文件与输出替换的统一事务锁；复核后的极小竞态窗口仍由调用环境负责避免外部写入。
- 进度是阶段级而非逐 ARXML 节点；耗时规划在下一安全边界响应取消。
- 本轮未实现 GUI、MCP 服务、服务安装、网络接口或后台守护进程。
- CLI 暂未切换到 Facade；它保留为稳定回归与开发入口。
