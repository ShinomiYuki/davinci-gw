# 第12轮开发日志：缺失 DBC 删除与专项路由组识别

## 本轮目标

本轮针对 E03 BEV/REEV 真实工程修复三个会影响正常输出的问题：

1. 信号 DELETE 的源 DBC 端点已经完全不存在时，旧逻辑仍按定位失败阻断，未遵守 DELETE 幂等语义。
2. 同一目标通道同时存在正式应用组和测试/专项组时，动态索引只看到两个完整 CanIf 候选，无法选出普通路由应使用的应用组。
3. 新增目标腿时，完整既有源 Rx 的 CAN 类型可能由 DBC 配置为 `STANDARD_FD_CAN`，而配置表按默认值填写 `STANDARD_CAN`；旧逻辑把这种仅源类型不同的复用场景当作冲突。

## 实现方案和安全边界

### 信号 DELETE 缺失端点

源 ComIPdu 不存在时，工具会检查 ComGwMapping 中真实的 Source/Destination 信号引用：

- DBC 端点和相关 Mapping 引用都不存在：输出 `SIGNAL_DELETE_NOT_FOUND` 警告，按“已经不存在”幂等跳过。
- DBC 端点不存在但 Mapping 仍保留匹配引用：输出 `SIGNAL_DELETE_DANGLING_REFERENCE` 错误并阻止写出，避免留下悬空路由。
- 端点歧义、Mapping 歧义和引用链不完整继续按原规则阻断。

匹配使用完整信号身份前缀和 Rx/Tx 后缀边界，不使用宽泛 substring。源端已经确认不存在时不再继续定位目标端，避免追加与真实根因无关的错误。

### 正式应用组与专项组

动态索引仍先沿成员的真实 PduR、EcuC、CanIf 和 TxBuffer 引用确认目标通道。只有多个结构完整的 CanIf 组把同一通道判定为主通道时，才把组名作为二次交叉证据：忽略大小写与分隔符后，名称必须严格以 `<通道>App` 结尾。

- 恰好一个候选满足该边界：它作为普通应用组；其他候选保持原样并输出一次 `PDUR_ROUTING_GROUP_SECONDARY_GROUP_IGNORED` 基线警告。
- 没有或有多个候选满足：保持 `PDUR_ROUTING_GROUP_CHANNEL_AMBIGUOUS` 阻断，不猜测。
- 生产代码没有写死 E03、DKCAN、具体组名或报文 ID。

REEV 中的真实触发结构是正式 `PduRRoutingPathGroup_DKCanApp` 与单成员专项 `PduRRoutingPathGroup_TEST_6E9_DKCan` 同时以 DKCAN 为主通道。本轮只让普通 ADD 使用正式组，不删除、不迁移、不修改专项组成员。

### 新增目标腿复用既有源 Rx

ADD 语义定位增加受控的“采用基准源类型”能力，仅在以下条件全部成立时生效：

- 源报文名、CAN ID、HRH、EcuC PDU、PduRSrcPdu、RoutingPath、长度、DLC 检查和上层回调等身份均完整且唯一。
- 唯一差异是配置表源类型与既有 CanIfRxPdu 类型不同。
- 基准类型属于工具支持的 CAN 类型枚举。
- 当前操作只复用源链并新增目标腿，不修改既有源 Rx。

满足时输出 `DIRECT_SOURCE_TYPE_FROM_BASELINE` 警告并采用 ARXML 现值。DELETE 仍保持严格类型匹配；非法枚举及其他任何源端冲突仍然阻断。

## 已知限制

- 正式应用组交叉检查要求唯一 `<通道>App` 名称边界；不符合既有命名约定且又与专项组冲突时仍会阻断，需要人工确认基线，不会自动选组。
- DBC 端点缺失但残留 Mapping 引用时，工具只报告并阻断，不会在缺少端点身份的情况下猜测删除。
- 基准源类型优先只适用于新增目标腿；DELETE 不会因配置表默认值不同而放宽定位。
