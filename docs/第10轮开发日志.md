# 第10轮开发日志：既有路由语义识别与自发报文隔离

## 问题与根因

E0Y 标准表中的 `ADS_COM_1`、`ADAS_ZCU_1`、`ADAS_ZCU_2` 四条直接报文 ADD，在原始基线中已经存在完整的 CanIfRx、PduRSrcPdu、RoutingPath、PduRDestPdu、EcuC、CanIfTx 和应用路由组引用。旧实现仍按当前 `GWT_...` 命名生成计划路径，再以完整路径判断 EXISTING，因此无法识别名称不同但引用关系完整的旧对象，并生成了第二套路由。再次使用该输出时，只会识别新生成的 `GWT_...` 对象；这不是自发报文误命中，而是 ADD 的既有对象判断依赖生成名称。

不能用增加 `Gw/GWT/GWH` 前缀列表解决：前缀不代表对象语义，项目还可能包含 DBC 名称或人工名称。生产代码现改为按完整引用链定位，名称只作为带明确边界的报文身份交叉检查，避免 `ABC_1` 误命中 `ABC_10`。

## 直接报文语义定位

新增集中式 `DirectRouteSemanticLocator`，由 ADD 和 DELETE 共用：

- 源端：报文名、CAN ID、HRH、CanIfRxPdu、EcuC PDU、RECEIVE/CanIf PduRSrcPdu、RoutingPath。
- 目标端：报文名、CAN ID、TxBuffer、CanIfTxPdu、EcuC PDU。
- 路由腿：已定位源 RoutingPath 下，唯一引用目标 EcuC PDU 的 TRANSMIT/CanIf PduRDestPdu。
- 结果显式区分 `MISSING`、`FOUND`、`PARTIAL_CONFLICT` 和 `AMBIGUOUS`，并携带候选完整路径。

ADD 根据状态只创建缺失部分：完整路由记为已存在；缺组成员时只补精确引用；源链已存在时只增加目标腿；目标端只有在已被普通 CanIf→PduR 应用路由使用时才允许复用。DestPdu 已属于错误组、多个组或诊断组时阻断，不自动迁移。

E0Y 中 ASU_1 等普通路由证明多个源 RoutingPath 可以共享同一目标 CanIfTx/EcuC，因此保留了有 PduR 应用路由证据时的端点复用。仅存在本地自发/COM Tx、没有普通 PduR 目标腿时，端点不是既有网关路由证据，也不能再创建同 CAN ID、同 TxBuffer 的第二套对象；工具会列出实际引用者并阻断。仅存在本地 Rx、没有 PduRSrcPdu 链时同样阻断。

## DELETE 与信号路由审查

DELETE 已改为使用同一个直接报文语义定位器，目标候选始终限定在精确源 RoutingPath 下。它不再要求 DestPdu 名称包含目标报文名，并补齐源/目标方向及 CanIf 模块引用校验；路径外同名、同 CAN ID 的自发 Tx 不会成为候选，也不会制造虚假歧义。删除仍按 `REMOVE_REFERENCE → 外部引用投影 → DELETE DestPdu → 共享上游对象判断` 执行。DELETE→ADD 同键替换在二次执行时可用 ADD 行的新参数重新确认同一引用链。

信号 ADD/DELETE 已逐项审查：Mapping 继续按 `ComGwSourceSignalRef`、Destination 继续按目标信号引用定位，源/目标方向、CAN/LIN 唯一性和 LIN 回退边界没有发现与直接报文同类的命名路径依赖，因此未重写信号定位器。第09轮加入的 Signal Access Mutation 保持有效：新建 Mapping、既有 Mapping 和只补 Destination 都会把实际源 Rx 与目标 Tx Signal Access 设置为 `ACCESS_NEEDED_BY_SWC_OR_COM`；DELETE 不回退 Access。

## 基线警告

保留第09轮对 `PDUR_ROUTING_GROUP_NON_MAIN_MEMBER` 的修正：按“组完整路径、异常成员完整路径、实际通道、主通道”稳定去重；归属为“基线 ARXML / PduR 路由组”，不绑定 Excel 行，也不附带当前处理路由的 DestPdu。T13J 的 DKCanApp/`FRZCU_6_DACAN` 与 GLCanApp/`BMS_2_G_50B_ICCAN` 各显示一次，继续作为不阻断的基线一致性警告。

## 测试与真实验证

开发阶段没有提前运行全量测试。针对性验证结果：

- 直接报文、DELETE、动态路由组、信号、GUI 和 ARXML 相关用例：`100 passed`。
- 新增错误路由组归属用例：`1 passed`。
- E0Y 原始基线代表性集成：四条目标路由全部识别为 EXISTING，统计为 `added=0, existing=4, skipped=0`，Mutation 为空。
- E0Y 已污染输出：检测到两条完整源链，返回 `DIRECT_SOURCE_CHAIN_AMBIGUOUS`，Mutation 为空，不生成第三套对象。
- 原始 E0Y 全表预览仍有一项与本轮无关的输入/基线冲突：第14行 ASU_2 的标准表要求 `STANDARD_CAN`，基线 CanIfRx 为 `STANDARD_FD_CAN`；工具按安全规则阻断，没有放宽源端类型校验。
- 最终完整回归：`202 passed, 2 skipped, 1 failed`，耗时 178.28 秒。唯一失败为真实 GUI 心跳最大间隔 1.265 秒，超过 `<1.0s` 阈值；输出生成、Prepared Session、取消、窗口交互、输入只读等功能断言均已通过。按既有环境时序抖动口径记录，不修改产品代码，也不重复全量。

真实输入的大小、修改时间和 SHA-256 在验证前后保持不变，没有生成迁移版 Excel，也没有覆盖基线或问题输出。

## 代码审查与修复

本轮审查完整 diff 和 ADD/DELETE、RoutingGroup、信号 Mapping/Access 的受影响调用点，实际发现并修复：

1. 路由组模型异常可能从端点证据扫描中泄漏为系统错误，改为只捕获明确的 `RoutingGroupModelError`，并在语义结果中形成可定位冲突；其他编程错误不被掩盖。
2. DestPdu 重复时，成员反查先于重复检测会抛异常，调整为先报告目标腿歧义。
3. 人工改名且目标语义冲突的路由腿曾被误判为 MISSING，改为在精确源路径内记录相关 EcuC 候选并阻断。
4. 一对多场景中相似报文名和不同 CAN ID 曾形成虚假冲突，调整为先以 CAN ID、TxBuffer 精确收窄，再做名称边界校验。
5. DELETE→ADD 同键替换第二次运行可能仍使用 DELETE 旧参数定位，增加同键 ADD 新参数的受控回退，保持引用链限定和幂等。
6. Windows 版本资源的数值元组落后于字符串版本，本次同步修正，后续构建同时核对 FileVersion 与 ProductVersion。
7. 审查发现非主通道成员提示虽已正确归属并去重，但正文仍缺少“主通道”；补齐主通道并增加真实 T13J 断言。
8. T13J 第8行 `DSA_RemoteDiag` 与已有 `BPC_RemoteDiag` 共享目标 CAN ID/TxBuffer，但报文名不同；早期候选范围过宽会把它误报为自发端点冲突。目标端候选现先按完整报文名边界收窄，同名端点仍严格校验并隔离自发 Tx，不同报文身份则允许按原规则新增。

生产代码没有 E0Y/T13J 项目组名、通道映射、TxBuffer 或 `Gw/GWT/GWH` 前缀枚举；没有加入自动清理历史重复配置的行为。
