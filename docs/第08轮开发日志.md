# 第08轮开发日志：动态应用路由组与语义 DELETE

## 本轮目的

上一轮把 `PduR路由组` 作为直接报文表的必填列，这改变了上游标准接口。本轮撤销该要求，恢复“直接报文路由”A:R 共 18 列标准格式。路由组属于基准 ARXML 的内部配置，工具应从真实引用关系推导，而不是要求用户把项目内部组名写回 Excel。

真实验收输入为只读的 `input/T13J.arxml` 和原始 `input/网关路由配置表_v4.84.xlsx`，没有创建或使用补列迁移版配置表。

## 动态应用组索引

`RoutingGroupMembershipService` 保留引用级 Mutation、精确成员增删、重复/悬空检查、删除投影和幂等能力，并新增动态索引。每个成员沿以下关系解析：

```text
PduRRoutingPathGroup/PduRDestPduRef
→ PduRDestPdu
→ EcuC PDU
→ 引用该 PDU 的 CanIfTxPdu
→ CanIfTxPduBufferRef
→ 工作簿“引用数据”的 CAN 通道
```

同时解析 `PduRDestPduPduRBswModulesRef → PduRBswModuleRef`，并与 CanIfTxPdu 所在 ECUC 模块完整路径交叉验证。这样应用/诊断分类依据模块和引用结构，而不是组名。纯 CanTp/DoIP 组不会进入普通报文候选；混合模块、链路不唯一或结构损坏会阻断。

每组按成员实际目标通道计数，唯一最高计数通道为主通道；最高计数并列时该组不可解析。反向要求一个目标通道只有一个主组。少数偏离成员只产生基线一致性警告，不会成为第二候选。

T13J 共解析 16 个路由组，其中 11 个普通应用组，动态结果为：

| 目标通道 | 主应用组 |
| --- | --- |
| BDCAN | PduRRoutingPathGroup_BDCanApp |
| CHCAN | PduRRoutingPathGroup_CHCanApp |
| DACAN | PduRRoutingPathGroup_DACanApp |
| DKCAN | PduRRoutingPathGroup_DKCanApp |
| DMCAN | PduRRoutingPathGroup_DMCanApp |
| EPCAN | PduRRoutingPathGroup_EPCanApp |
| GLCAN | PduRRoutingPathGroup_GLCanApp |
| ICCAN | PduRRoutingPathGroup_ICCanApp |
| LCCAN | PduRRoutingPathGroup_LCCanApp |
| PTCAN | PduRRoutingPathGroup_PTCanApp |
| SUCAN | PduRRoutingPathGroup_SUCanApp |

这些值只存在于真实输入集成断言和本文验收记录，生产代码没有项目专用映射。

T13J 的 `DKCanApp/FRZCU_6_DACAN` 与 `GLCanApp/BMS_2_G_50B_ICCAN` 被识别为非主通道成员并显示组名、DestPdu 路径、解析通道、报文名称和 CAN ID。DGCAN 虽存在于“引用数据”，但没有普通应用组，因此直接报文目标为 DGCAN 时明确阻断，不会回退到 DCAN/CanTp 诊断组。

## ADD 与 DELETE

ADD 继续先完成源/目标链预检。目标端使用工作簿通道、唯一 TxBuffer、目标报文名、CAN ID 和 EcuC 引用确认身份；即使 CanIfTxPdu 与 DestPdu 尚待创建，也可使用已预检 Mutation 的目标身份选择主应用组。DestPdu 和成员均存在时幂等跳过，只有成员缺失时只补精确引用。

DELETE 不再拼接 `GWT_...` 路径。源端按报文名、CAN ID、HRH、CanIfRxPdu、EcuC PDU、PduRSrcPdu 和 RoutingPath 定位；目标端限定在该 RoutingPath 的 DestPdu/EcuC 引用集合内，再按 CAN ID、TxBuffer 和 CanIfTxPdu 定位。对象名中的报文名称只做下划线边界交叉检查，不依赖 `GWT`、`GWH`、`Gw` 或无前缀等项目命名。`ABC_1` 不会匹配 `ABC_10`。

目标候选必须属于已锁定源 RoutingPath 的 DestPdu 引用链，因此同名同 ID、但未被该路径引用的本地自发 Tx 报文不会被选中。0 个真实路由腿候选按幂等 DELETE 处理；多候选、部分链、名称冲突或实际组与主组不一致均阻断。成功顺序保持：精确 `REMOVE_REFERENCE` → 外部引用投影 → DestPdu → 按共享关系处理上游对象。

## 代码审查与修复

本轮逐项审查完整 diff 和受影响调用点，实际发现并修复：

- 初版名称交叉检查仅列举 `GWT_`/`Gw_`，会漏掉 `GWH_` 和其他前缀；改为与前缀无关的完整报文名边界匹配，并增加自发 Tx 排除测试。
- 初版把引用数据中任意复用 TxBuffer 当成全局错误，会让无关源通道阻断合法目标路由；改为只在应用组成员或当前目标行实际使用该 Buffer 时判断歧义。
- 初版主要通过 CanIfTx 反查排除诊断组，未核对 DestPdu 的模块引用；增加 PduRBswModuleRef 与 CanIf 模块完整路径交叉验证。
- DELETE 仍可能把“目标 CanIf 对象存在但名称不符”误当成幂等不存在；现在识别为部分语义链并阻断。
- 旧的按组名查询私有方法已无调用，删除死代码，生产代码未保留 T13J 组名或 TxBuffer 哈希。
- 问题文本统一携带源/目标报文名称、十六进制 CAN ID 和通道；路由组问题继续包含组名和对象完整路径，GUI 可直接显示与检索。
