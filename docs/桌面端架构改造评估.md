# 桌面前端架构改造评估报告

| 项目 | 内容 |
| --- | --- |
| 评估对象 | davinci-gw v1.2.2（commit `0f9e2c7`，分支 `frontend-fix`） |
| 评估问题 | 桌面端是否改用 C# 或 Electron 重写，并新增本地端口（Port）调用后端 MCP 能力 |
| 核心结论 | **不建议换栈重写。** 建议走"桌面端瘦客户端化"路线：先做无端口的 stdio 子进程方案，本地端口作为可选的第三阶段；若最终仍决定换栈，选 C#，不选 Electron |
| 证据基础 | 仅读代码走查，未运行测试、未构建发布包（相关未验证项已在第 8 节逐条标注） |

## 1. 结论速览

| 原始诉求 | 判断 | 关键依据 |
| --- | --- | --- |
| 桌面端复用 MCP 能力 | **成立，是真问题** | 桌面端目前把核心代码**随包分发、进程内调用**（`src/UI/task_runner.py:38-40` 直接 `new GatewayFacade()`），MCP 自迭代出的修复无法送达同事端 |
| 桌面端加 Port（本地端口） | **可行但非必需，且非首选** | MCP SDK 2.x 原生支持 stdio / Streamable HTTP / SSE，且自带客户端；但仓库三处明文承诺"不监听端口"（`src/davinci_gw/mcp/__main__.py:12`、`README.md:68`、`docs/MCP本地安装与使用.md:5`），且已有测试断言 MCP EXE 无 TCP 连接（`tests/integration/test_mcp_executable.py:85-111`） |
| 桌面端改用 C# / Electron | **不建议** | 桌面端**已经是瘦客户端结构**，无任何业务规则（UI 对 `davinci_gw` 的 import 只涉及 `contracts` DTO、`application.facade`、`runtime` 三个模块）。换栈解决不了真正的矛盾，只会重写 UI 层、构建层、发布层和 4 个 GUI 测试 |
| 真正该做的事 | **补契约缺口 + 核心单点化** | MCP 与 GUI 存在 4 处能力差集（第 2.5 节），它们是"桌面端瘦下来"的前置条件，与选型无关 |

**一句话**：矛盾的本体是"核心逻辑有两份拷贝，一份在同事手上的离线包里"，而不是"UI 用什么语言写"。解法是**让桌面端不再持有核心**，而不是**用另一种语言重写桌面端**。

## 2. 事实基线

### 2.1 桌面端已经是瘦客户端结构（关键发现）

`src/UI` 对 `davinci_gw` 的完整 import 关系：

| UI 文件 | 导入内容 | 类别 |
| --- | --- | --- |
| `src/UI/issue_model.py:7` | `contracts.IssueDto` | DTO |
| `src/UI/main_window.py:33` | `contracts.FeatureSummaryDto` | DTO |
| `src/UI/view_model.py:12-21` | `contracts.{CheckResultDto, FeatureSummaryDto, GenerationResultDto, InputFileDto, IssueDto, OperationStatus, PreparedSessionDto, ProgressEventDto}` | DTO |
| `src/UI/detail_dialog.py:16` | `contracts.FeatureSummaryDto` | DTO |
| `src/UI/task_runner.py:9` | `application.facade.GatewayFacade` | 应用服务 |
| `src/UI/task_runner.py:10` | `contracts.{ProgressEventDto, UpdateRequestDto}` | DTO |
| `src/UI/task_runner.py:11` | `runtime.CancellationToken` | 运行时 |

**UI 没有 import 过** `input` / `routing` / `arxml` / `modules` / `domain` / `validation` 中的任何一个模块。路由生成、Excel 读取、ARXML 解析、诊断映射、校验规则全部在核心，桌面端一条都没有实现。文档同样写明："桌面版只编排已有 `GatewayFacade`，不新增路由规则"（`docs/GUI.md:59`）。

所有跨边界数据都是 `SerializableDto` 子类，具备 `to_dict()` / `to_json()`（`src/davinci_gw/contracts/models.py:38-49`），不含异常链或内部 ARXML 对象。**这意味着"UI 只做展示、通过 IPC 传输 DTO"在类型层面已经成立，不需要改动契约结构。**

桌面端唯一入口是 `GatewayFacade`，且实例在 worker 线程内创建与释放（`src/UI/task_runner.py:38-40`、`:42-52`、`:54-65`）。

### 2.2 但核心是"随包分发的进程内副本"

GUI 与 MCP 是两套独立的 PyInstaller onedir 产物，各自打包了一份 `src`：

| | GUI | MCP |
| --- | --- | --- |
| spec | `packaging/davinci-gw-gui.spec` | `packaging/davinci-gw-mcp.spec` |
| 形态 | onedir，`console=False`（`gui.spec:35-55`） | onedir，`console=True`（`mcp.spec:32-52`） |
| 入口 | `packaging/gui_entry.py:5` → `UI.__main__.main` | `packaging/mcp_entry.py:3` → `davinci_gw.mcp.__main__.main` |
| 运行时 | 内置 `_internal`（含 Python 与全部依赖） | 内置 `_internal` + `codex_cli_bin` + `openai_codex`（`mcp.spec:10,18`） |

后果很直接：MCP 侧通过自动修复产出的修复（`hotfix/mcp-auto-*` 分支 → 合并 `main`）只进入**源码仓库**，同事手上的 GUI ZIP 里仍是修复前的那份核心代码。**修复到不了同事端**，这是当前架构真正的痛点。

### 2.3 MCP 侧是纯 STDIO，仓库明确承诺不监听端口

- `src/davinci_gw/mcp/__main__.py:15` → `build_server().run(transport="stdio")`；同文件 `:12` 文档字符串写明"只启动 STDIO；绝不开放网络传输或监听端口"。
- `src/davinci_gw/mcp/server.py:1` 文件头写明"官方 MCP SDK 2.x 的纯 STDIO 服务定义"。
- 全仓搜索 `http.server|socketserver|QTcpServer|QLocalServer|flask|fastapi|uvicorn|aiohttp|localhost|0.0.0.0` 在 `src/` 下**零命中**。
- `tests/integration/test_mcp_executable.py:85-111` 用 `Get-NetTCPConnection` **断言 MCP EXE 进程除 Proactor 内部配对外无任何 TCP 连接**。

也就是说：**本地端口是全新能力，不是复用现成实现**；同时它会与一条被自动化测试固化的安全承诺正面冲突。

### 2.4 交付链路：GUI 没有 CI，版本号散落 9 处

| 事实 | 证据 |

## 3. 问题重述：真正的矛盾是什么

原始诉求里混了三个互相独立的命题，必须拆开看：

- **(a) 桌面端复用 MCP 能力** —— 真问题。当前核心有两份拷贝，同事端的那份永远不会自动更新。
- **(b) 桌面端加 Port** —— (a) 的一种实现方式，不是唯一方式。stdio 子进程同样能让"核心只存在于后端进程"。
- **(c) 桌面端改用 C# / Electron** —— 与 (a)(b) **正交**。用 Python 写客户端一样可以只做展示；用 C# 写客户端如果仍然内嵌核心，问题原样存在。

所以真正要回答的问题是：**"如何让同事端不再持有核心代码的副本，并让自迭代出的修复能到达他们"。**

换语言只是换掉了"副本"里 UI 那一半的载体，**没有动到"副本"这件事本身**。

## 4. 候选方案对比

| 维度 | A 现状 | B 瘦客户端·stdio 子进程 | C 瘦客户端·本地端口 | D C# 重写 + 端口 | E Electron 重写 + 端口 |
| --- | --- | --- | --- | --- | --- |
| 核心副本数 | 2（GUI 一份、MCP 一份） | 1（仅后端进程） | 1（可集中为内网服务） | 1 | 1 |
| 修复可达同事端 | 否 | 是（随后端包升级） | 是（服务端升级，客户端零改动） | 是 | 是 |
| 是否违反"不监听端口"承诺 | 否 | 否 | **是**，需重写 3 处文档并调整 1 个测试 | 是 | 是 |
| 后端改动量 | 无 | 小（新增客户端传输层） | 中（新增 HTTP 传输 + 鉴权 + 会话跨客户端管理） | 中 | 中 |
| 客户端改动量 | 无 | 中（换掉 `task_runner` 的执行层） | 中 | **大**（重写 10 个 UI 文件 + 4 个 GUI 测试） | **更大**（重写 + 前端工程化） |
| 打包链路改动 | 无 | 中（GUI 包需附带后端 exe） | 中 | 大（弃用 PyInstaller，换 `dotnet publish`） | 大（换 electron-builder，破坏 `_internal` 布局与许可证收集） |
| 交付体积（客户端） | 不变 | 约翻倍（两个 onedir） | 很小（纯客户端） | 中（self-contained 约 60–90MB） | 大（150–250MB + Chromium） |
| GUI 测试资产 | 保留 | 需把 `test_gui.py` 改为契约 mock | 同 B | **作废重写**（pytest-qt 无法复用） | **作废重写** |
| 离线可用性 | 最好 | 好（后端本地进程） | 依赖服务可达 | 依赖服务可达 | 依赖服务可达 |
| 新增技术栈 | 无 | 无 | 无 | C# / .NET | Node / TS |
| 团队技能要求 | 不变 | 不变 | 不变 | 需要 C# 能力 | 需要前端工程能力 |
| 经验估算工期 | — | 3–5 人日 | 5–8 人日 | 15–25 人日 | 25–40 人日 |

> 工期为基于文件规模与调用链的经验估算，未实测；不含第 7 节的前置加固项。

## 5. 推荐路线

### Phase 0 — 契约对齐（必须先做，与选型无关）

让 MCP 暴露的能力与 GUI 所需能力等价，否则 Phase 1 无路可走：

1. `preview_gateway_update` 响应补 `checks`（`CheckResultDto` 列表）——GUI"输入检查"区依赖它（`src/UI/main_window.py:337-341`）。
2. `IssueDto` 增加 `advice` 字段（`src/davinci_gw/contracts/models.py:124-141`），把 UI 硬编码的建议表（`src/UI/issue_model.py:49-64`）下沉到后端；MCP 的 `GatewayToolResponse` 同步。
3. 增加 `discard_prepared` / `cleanup_expired` 两个只读-写工具，对应 `facade.discard_prepared` / `facade.cleanup_expired`。
4. 进度通道：MCP 侧补一个可订阅的进度通道（现只有日志式进度，`src/davinci_gw/mcp/service.py:21-28`）。
5. 删掉 UI 侧三处弱于核心的重复判定：输出路径校验（`src/UI/output_paths.py:25-42`）、DoIP 指纹复核（`src/UI/view_model.py:136-148`）、DoIP 前置判定（`src/UI/view_model.py:253-254`），一律以后端返回为准。

### Phase 1 — 桌面端瘦客户端化（不加端口，推荐）

- 桌面端从"内嵌核心"改为"启动后端子进程 + MCP 客户端调用"。
- MCP SDK 2.x 已原生支持三种传输并自带客户端，**不需要引入任何新依赖**；stdio 子进程是其中最简单的一种，且**继续满足"绝不监听端口"的现有安全承诺**。
- 关键杠杆点：`src/UI/task_runner.py` 是唯一直接持有 `GatewayFacade` 的地方（`:38-81`）。只要把它换成 `GatewayClient`，保持 `progress` / `preview_finished` / `generation_finished` / `stopped` 四个信号形状不变，**`view_model.py` 与 `main_window.py` 基本无需改动**。
- 打包：GUI 包内附带后端 exe（两个 onedir 子目录），同事仍然是"解压双击、零环境"。

### Phase 2 — 本地端口（可选，解锁集中升级与任意客户端）

只有当出现"后端集中部署、同事端零重发"的需求时才做：

- 传输层：MCP SDK 2.x 的 Streamable HTTP，绑定 `127.0.0.1` + 随机端口 + 启动时一次性令牌；或独立入口 `davinci-gw-service`，避免与 `davinci-gw-mcp.exe` 混用。
- 必须同步处理：
  - `src/davinci_gw/mcp/__main__.py:12`、`README.md:68`、`docs/MCP本地安装与使用.md:5` 三处"不监听端口"承诺的措辞。
  - `tests/integration/test_mcp_executable.py:85-111` 的"无 TCP 连接"断言范围（建议**新开独立服务入口**，让该断言继续只约束 MCP EXE）。
  - 路径与输出安全规则（`src/davinci_gw/mcp/paths.py:66-112`、`docs/MCP本地安装与使用.md:119-126`）在有监听方时需要重新评估。
  - 会话隔离：Prepared Session 现在是进程内内存工作树，默认 15 分钟过期、最多 8 个（`src/davinci_gw/contracts/models.py:224-225`、`src/davinci_gw/application/facade.py:62-63`），长驻服务下必须按客户端隔离，避免会话串味。
- 客户端增加"服务地址"配置项：留空 = 本地后端子进程；填写 = 连接内网服务。

### Phase 3 — UI 技术栈复评（可选，有数据再做）

到 Phase 2 稳定后，若仍有"界面交互体验"或"团队技能"诉求，再基于真实使用反馈评估 C#/Electron（见第 6 节）。**不要在没有 Phase 1/2 数据的情况下先做栈迁移。**

## 6. 若一定要换栈：C# 与 Electron 怎么选

### 6.1 结论：选 C#（WPF 或 Avalonia），不选 Electron

| 维度 | C#（WPF / Avalonia） | Electron |
| --- | --- | --- |
| 分发体积 | self-contained 单文件约 60–90MB；framework-dependent 可再降 | 150–250MB（含 Chromium） |
| 内存占用 | 数十 MB 级 | 200MB+ 起步，多进程模型 |
| 启动速度 | 快 | 慢（Chromium 冷启动） |
| 与 Python 后端协作 | 命名管道 / HTTP / gRPC 均成熟；官方 MCP C# SDK 可直接用 | 同样可用，但需自建桥接或走 HTTP |
| 内网免安装分发 | 单 exe + 少量依赖，团队已有 `dotnet publish` 经验即可 | 需 electron-builder，产物结构复杂，第三方许可证收集要重做 |
| 杀软误报 / 签名 | 相对可控 | 较高（Electron 打包特征明显） |
| 团队技能 | 需补 C# / WPF | 需补前端工程化（构建、打包、CI） |
| 与本项目界面匹配度 | 表单 + 表格 + 摘要卡片，原生控件够用 | 优势在复杂富文本 / 图形化编辑器，本项目用不上 |

Electron 的真实优势（前端生态、组件库、跨平台、复杂表格/图形编辑）在本项目**几乎没有兑现空间**：当前界面是 4 步表单 + 7 列问题表 + 摘要卡片 + 2 个对话框（`src/UI/main_window.py:92-434`），原生控件完全够用。而代价是分发体积、内存、冷启动和企业内网分发体验的全面劣化。

### 6.2 换栈的真实成本（不是写界面）

1. **GUI 测试资产作废**：`tests/unit/test_gui.py:136,162`（pytest-qt `qtbot`）与 `tests/integration/test_gui_real.py:32-102`（真实点击 + 取消 + 80MB 输出 + 基准指纹未变的端到端验收）都无法直接复用，需要用新栈重建等价物。
2. **打包链路整体替换**：`packaging/davinci-gw-gui.spec`、`packaging/gui_entry.py`、`scripts/build_gui_release.ps1:32-79`（含 `_internal` 布局假设、第三方许可证收集、`SHA256SUMS` 只写 exe 一行的逻辑）全部需要重写。
3. **Windows 版本资源改由 csproj / electron-builder 承载**，`packaging/gui_version_info.txt` 的 `ProductName` / `FileDescription` 与 MCP 并列的命名需要重新落地。
4. **版本硬编码点从 9 处增加到 11+**，而 GUI 侧目前连版本一致性校验都没有。
5. **`docs/GUI.md` 本身就是 GUI 发布包内的 `README.md`**（`scripts/build_gui_release.ps1:47`），产物形态一变，全部发布说明与使用文档都要改。

**换栈解决不了核心矛盾**：新客户端若仍内嵌核心，问题原样存在；若改成远程调用，那收益来自"进程外调用"这个架构决策，与语言无关。
