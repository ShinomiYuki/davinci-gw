# 第09轮开发日志：信号 Access 与基线告警修正

## 背景

使用第08轮输出 `T13J_v4.84.arxml` 更新 DaVinci 工程后，直接报文和信号 Mapping 均能正常导入，但两个新增信号路由的源端 Rx、目标端 Tx `Signal Access` 仍为 `ACCESS_UNCLEAR`，需要人工改成 `ACCESS_NEEDED_BY_SWC_OR_COM`。

同时，第08轮能够正确识别 `DKCanApp/FRZCU_6_DACAN` 和 `GLCanApp/BMS_2_G_50B_ICCAN` 两个非主通道成员，但警告被绑定到正在处理的 Excel 路由，重复显示，并给出“检查输入”的错误建议。

## 实现

### 信号 Access

- 新增独立 `COM_SIGNAL_ACCESS` Mutation，不把 Access 伪装成超时参数。
- 只有源端 Rx 与至少一个目标端 Tx 已经成功参与 `ComGwMapping` 时才规划 Access。
- 现有值为 `ACCESS_UNCLEAR` 或其他单值时更新为 `ACCESS_NEEDED_BY_SWC_OR_COM`；目标值已经存在时幂等跳过。
- 参数缺失时从基线中的真实 `ComSignalAccess` 枚举参数克隆节点；重复参数、缺少 VALUE 或缺少真实模板时阻断。
- Mapping 已存在但 Access 未更新的上一版输出，重跑时只补齐参数。
- DELETE 不回退 Access。信号可能仍被 SWC、COM 或其他路由使用，在没有引用归属证据时回退会误伤人工配置。
- `MutationContext` 登记既有 VALUE 的原文，后续应用失败时会同时恢复文本和移除新增节点。

### 基线告警

- 非主成员继续参与主通道统计，但不污染反向通道映射，检测规则未改变。
- 基线警告保留空 `SourceLocation`，文件位置指向输入 ARXML，不再借用 Excel 行、源/目标报文身份或当前 DestPdu。
- DELETE 与 ADD 各自解析到相同基线警告时，在事务合并处按代码、消息、级别和基线文件精确去重。
- GUI 对 `PDUR_ROUTING_GROUP_NON_MAIN_MEMBER` 显示“核对基线 ARXML 成员归属，工具不会自动迁移”，不再提示检查 Excel 输入。

## 测试

- 信号、动态路由组和 GUI 增量测试：`24 passed`。
- 审查修复后扩展增量测试（含重复 Access 阻断和文本回滚）：`36 passed`。
- 真实 `T13J.arxml + 网关路由配置表_v4.84.xlsx` preview→commit：`1 passed`。四个 TMS Rx/Tx 信号均写入 `ACCESS_NEEDED_BY_SWC_OR_COM`；两个基线异常成员各显示一次，没有工作表行、当前报文身份或当前 DestPdu。
- 最终完整回归：`192 passed, 2 skipped, 1 failed`。唯一失败是已知 GUI 心跳环境时序抖动，阈值 `<1.0s`、本机最大间隔 `1.297s`；取消、预览、生成、单次基线解析、输出文件和界面更新等功能断言均已通过，按既定边界记录而未修改产品代码或重复全量回归。
- 发布包验证：MCP EXE 的完整 STDIO、四工具调用和 EOF 退出测试 `2 passed`；GUI EXE 离屏隐藏启动 5 秒后仍正常运行，启动冒烟通过。

## 代码审查与修复

1. 首版辅助函数插入位置切断了直接路由 `_issue()` 的返回语句，使 DGCAN 缺应用组场景被包装成系统错误；已修复并恢复原业务错误码。
2. 首版 Access 检查只读取参数语义，缺少 VALUE 的节点会延迟到应用阶段失败；已改为在规划阶段检查参数节点数量和唯一 VALUE。
3. Access 曾临时复用超时参数构造函数；已拆分独立模板克隆和 UUID 种子，保持职责清晰。
4. 修改既有 VALUE 原先不在回滚登记中；已增加文本变更回滚并补充单元测试。
5. 核对了已有 Mapping 修复、一对多目标、参数缺失克隆、重复参数阻断、输出参数复核，以及 DELETE 不回退 Access 的安全边界。
